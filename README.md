# 실시간 날씨 정보와 AI가 결합된 새로운 날씨 플랫폼, WeatherWise

</br>


## 🔖 프로젝트 개요
**주제**: 사용자 맞춤형 날씨 정보 제공 및 상호작용 플랫폼  
**대상**: 날씨 정보 활용 및 상호작용에 관심이 있는 사용자  

</br>

## 🎯 목표
1. **정확한 날씨 정보 제공**: 기상청 데이터와 AI 분석을 통해 지역별 맞춤형 날씨 정보 전달  
2. **미션 수행과 커뮤니티 강화**: 날씨 기반 미션과 커뮤니티 상호작용을 통해 사용자 참여 유도  
3. **긴급 상황 대응**: 기상특보 채팅으로 실시간 정보 공유 및 대응  


</br>

### **AI / Automation**

## 🔗 주요 기능


### 1️⃣ 회원 및 인증 관리 시스템
- **JWT 기반 사용자 인증**  
  - 사용자 로그인/회원가입 시 JWT 토큰 발급 및 인증 관리.  
  - STOMP 헤더에 JWT 토큰을 포함해 실시간 채팅에서도 인증 처리.  
  - 토큰에서 사용자 ID를 추출하여 커뮤니티, 미션 등 다양한 기능에 활용.  

- **회원가입 및 로그인**  
  - 일반 회원가입 및 카카오 소셜 로그인 지원.  
  - 비밀번호 검증 및 닉네임 중복 방지 처리.  

- **사용자 정보 관리**  
  - 사용자 정보 수정, 닉네임 변경, 로그아웃 및 회원 탈퇴 기능 제공.  

### 2️⃣ 미션 생성 및 인증
- **날씨 기반 맞춤형 미션 제공**  
  - 기상 데이터를 활용하여 아침, 점심, 저녁 기준으로 최대 3개의 미션 생성.  
  - 예시 미션: \"자전거를 타세요\", \"텀블러를 사용하세요\".  
  - 각 미션마다 포인트 지급률 및 진행 상태 표시.  

- **AI 기반 미션 인증**  
  - 사용자가 미션에 맞는 사진을 첨부하면 AI가 해당 사진의 적합성을 검증.  
  - 인증 성공 시 포인트 지급 및 실패 시 재도전 가능.  

- **포인트 및 랭킹 시스템**  
  - 포인트를 기반으로 사용자 랭킹 제공.  
  - 순위 확인 및 검색 기능을 통해 사용자 경험 향상.  

### 3️⃣ 커뮤니티
- **위치 기반 게시글**  
  - 사용자의 현재 위치를 기준으로 반경 5km 내 게시글 표시.  
  - 위치 변경 시 카카오맵 API를 통해 새로운 위치 반영 및 게시글 업데이트.  

- **게시글 작성**  
  - 제목(20자) 및 본문(150자) 글자 수 제한을 통해 사용자 경험 최적화.  
  - 좋아요/싫어요 버튼으로 게시글 신뢰도 평가 가능.  

- **내가 작성한 글 관리**  
  - 사용자가 작성한 글의 리스트를 확인 및 삭제 가능.  

### 4️⃣ 기상특보 오픈채팅
- **기상특보에 따른 실시간 채팅방 생성**  
  - 기상특보 발생 시 해당 지역의 사용자들을 위한 오픈 채팅방 자동 생성.  
  - 예: \"강원도 건조/한파 경보 채팅방\".  
- **기상특보 데이터 업데이트**:
  - Spring Scheduler를 활용해 1시간마다 기상청 API 호출.
  - 기상특보 발령 시 '시/도' 기준으로 실시간 단체 오픈채팅방 자동 생성.
- **실시간 채팅**:
  - **Redis**:
    - 최신 채팅 메시지 100개를 캐싱하여 빠른 채팅 로드 제공.
    - 사용자 간 실시간 메시지 교환 성능 향상.
  - **WebSocket + STOMP**:
    - 실시간 양방향 통신 구현.
    - 채팅방 내 메시지 브로드캐스팅 및 실시간 알림 기능 제공.

### 🌈 개선 사항

  #### 1️⃣ 커뮤니티 (도움돼요/도움안돼요) 동시성 문제 해결 - <ins>실행 시간 약 84% 감소</ins>

  </br>

  **문제 상황**
  - 커뮤니티의 도움돼요/도움 안 돼요는 멀티스레드 환경에서 여러 스레드가 동시에 카운트를 업데이트할 때, 공유 자원에 대한 동기화 처리가 부족해 Race Condition 문제가 발생할 가능성이 있어 이를 확인하기 위해ExecutorService 를 사용해 동시성 테스트를 진행한 결과 카운트 값이 정확히 반영 되지 않는 문제가 발생했습니다.

  **문제 원인**
  - 여러 스레드가 동시에 같은 자원(도움돼요/도움 안 돼요)을 수정할 때 RaceCondition 이 발생했고, 이는 공유 자원에 대한 동시 쓰기 접근을 안전하게 제어하지 못 해서 일어난 것 입니다.

  **해결**=
  - DB Level , Application Level , 외부 시스템을 활용해 다양한 방법으로 동시성 문제를 해결해봤습니다.
  1. MySQL 비관적 락 : DB Level에서 가장 직접적이고 확실한 락을 걸어 동시어 접근하는 트랜잭션을 대기 시키면서 충돌을 없애기 위해 사용했습니다.
     
  2. MySQL 낙관적 락 : 항상 락을 거는 것이 아닌 충돌이 발생한 시점에만 재시도를 하면서 처리하기 위해 사용했습니다.
     
  3. 트랜잭션 격리 수준을 SERIALIZABLE로 설정 : SERIALIZABLE 은 논리적으로는 모든 트랜잭션을 순차적으로 실행한 것과 동일한 결과를 보장하기 때문에 락을 명시적으로 걸지 않고 동시에 같은 데이터를 수정하려는 시도를 강력하게 제어하기 위해 사용했습니다.
     
  4. ReentrantLock : DB Level이 아닌 Application Level에서 직접 락을 제어하고 싶어 사용해봤고, Java 에서 제공하는 Lock 을 사용하면 추가되는 인프라 비용 없이 세밀한 제어를 할 수 있어 사용했습니다.
     
  5. Kafka :  단순히 Lock 을 거는게 아니라 도움돼요/도움 안 돼요를 클릭한 이벤트를 비동기 큐에 넣고 순차 처리를 해서 동시성을 해결하기 위해 사용했습니다.Kafka 는 높은 트래픽 환경에서도 안정적이기 때문에 다른 해결 방법 보다 더 나은 성능 개선을 해보고 싶어 사용해봤습니다.
